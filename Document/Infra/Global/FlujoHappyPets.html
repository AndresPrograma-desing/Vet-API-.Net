🐾 happy pets · visión general del sistema

Cómo está hecho Happy Pets, de punta a punta

Para alguien que nunca tocó este código: qué hace el sistema, cómo se hablan el backend (vet-api-Net) y el frontend (vet-system-WEB), y cómo viaja un dato real desde que se pide hasta que se pinta en pantalla. No es referencia exhaustiva — al final hay un mapa a la documentación completa de cada módulo.

01Qué es Happy Pets

Happy Pets es el sistema de gestión de una clínica veterinaria, dividido en dos proyectos separados que se comunican por HTTP/JSON:

⚙️vet-api-Net — el backend. API REST en ASP.NET Core (.NET 10) que contiene toda la lógica de negocio y la base de datos.
🖥️vet-system-WEB — el frontend. Aplicación React (Vite) que consume esa API y la presenta como un panel según el rol del usuario.

No hay lógica de negocio real en el frontend: calcula, valida formularios y pinta pantallas, pero las reglas (¿se puede agendar esta cita?, ¿hay stock?, ¿cuánto es la factura?) viven siempre en el backend.

  • Portal de Clientes (/portal-cliente): acceso público para que el dueño de la mascota consulte su información, sin rol operativo.

Puntos clave de esa comunicación

🔌Un único cliente HTTP en el frontend: todas las llamadas pasan por request() en client.js. Está prohibido usar fetch directo en componentes — siempre se agrega una función nueva en src/services/api/index.js y se consume desde un hook.
🔑Autenticación JWT: al iniciar sesión, el backend devuelve un token. El frontend lo guarda (sessionStorage + localStorage, vía storage.js) y client.js lo inyecta como header Authorization: Bearer .... Si el backend responde 401, el cliente dispara logout() automáticamente.
🌐Mismo contrato, dos idiomas: el backend modela el dominio en español (Mascota, Cita, Factura) pero serializa los DTOs en snake_case vía [JsonPropertyName]. El frontend además tolera inconsistencias heredadas (rol/role, contenido/content) normalizándolas en la capa de servicios/hooks.
📡Tiempo real: mensajería y notificaciones usan SignalR (WebSockets); varias pantallas (citas, facturación) además refrescan por polling periódico (usePolling.js).
🧪Modo sin backend (Dummy Mode): el frontend puede simular todas las respuestas desde src/dummy/db.json sin tocar la red. Se activa con una clave en localStorage (USE_DUMMY_DATA).

03El flujo dentro de cada lado

Backend: 3 capas estrictas

Controller  →  Service  →  Repository  →  AppDbContext (EF Core)  →  Base de datos
  • Controller: recibe el HTTP request, lee rutas desde Constants/EndpointRoutes.cs, delega al Service, traduce el resultado o la excepción a un código HTTP. Nunca toca la base de datos ni contiene reglas de negocio.
  • Service: toda la lógica de negocio (¿el horario está libre?, ¿hay stock?, ¿cómo se calcula la factura?). Si algo viola una regla, lanza una excepción tipada que el Controller atrapa.
  • Repository: el único lugar que conoce AppDbContext. Ahí van los Where/OrderBy/Skip/Take reales sobre IQueryable, para que EF Core los traduzca a SQL en vez de traer toda la tabla a memoria.

Cómo se consulta realmente la base: el ORM

El Repository nunca escribe SQL a mano. Usa Entity Framework Core, un ORM (Object-Relational Mapper): traduce código C# (LINQ sobre IQueryable<T>) a SQL, y las filas que vuelven de la base en objetos C# otra vez. EF Core decide el SQL exacto según el motor configurado (PostgreSQL vía Npgsql, o MySQL vía Pomelo).

Ejemplo real — CitaRepository.GetPagedWithRelationsAsync

vet-api-Net/Repository/CitaRepository.cs 
var query = _context.Citas
    .Include(c => c.Mascota).ThenInclude(m => m.Cliente)
    .Include(c => c.Mascota).ThenInclude(m => m.Especie)
    .Include(c => c.Doctor)
    .Include(c => c.Secretaria)
    .Include(c => c.MetodoPago)
    .AsQueryable();

if (doctorId.HasValue)
    query = query.Where(c => c.DoctorId == doctorId.Value);

if (!allDates)
{
    var targetDate = (date ?? DateTime.Today).Date;
    query = query.Where(c => c.FechaCita.Date == targetDate);
}

if (!string.IsNullOrWhiteSpace(status))
    query = query.Where(c => c.Estado != null && c.Estado.ToLower() == status.ToLower());

return await query
    .OrderByDescending(c => c.FechaCita)
    .ThenByDescending(c => c.HoraCita)
    .ToPagedResultAsync(pageNumber, pageSize); // aplica Skip/Take internamente
  • _context.Citas es un DbSet<Cita> — EF Core lo mapea a la tabla Citas. Todavía no toca la base: solo está armando la consulta (IQueryable<Cita>).
  • .Include() / .ThenInclude() traen de una sola vez las relaciones (mascota, dueño, doctor...) — en SQL se traduce en JOIN, evitando el problema clásico de "N+1 queries".
  • .Where(...) encadenado se combina en una sola cláusula WHERE ... AND ... del SQL final.
  • .OrderByDescending(...).ThenByDescending(...) se traduce a ORDER BY fecha_cita DESC, hora_cita DESC.
  • ToPagedResultAsync(...) aplica Skip/Take (OFFSET/LIMIT) y calcula el COUNT(*) total. Recién ahí EF Core ejecuta la consulta.

El SQL que efectivamente se dispara (simplificado)

SELECT c.*, m.*, cl.*, e.*, d.*, s.*, mp.*
FROM "Citas" c
LEFT JOIN "Mascotas" m ON m."Id" = c."MascotaId"
LEFT JOIN "Clientes" cl ON cl."Id" = m."ClienteId"
LEFT JOIN "Especies" e ON e."Id" = m."EspecieId"
LEFT JOIN "Usuarios" d ON d."Id" = c."DoctorId"
LEFT JOIN "Usuarios" s ON s."Id" = c."SecretariaId"
LEFT JOIN "MetodosPago" mp ON mp."Id" = c."MetodoPagoId"
WHERE c."DoctorId" = @doctorId
  AND c."Estado" ILIKE @status
ORDER BY c."FechaCita" DESC, c."HoraCita" DESC
OFFSET @skip LIMIT @pageSize;
⚠ Por qué esto va en el Repository y no en el Service: mientras la consulta sea un IQueryable (no "materializada" con .ToListAsync()), todo el filtrado se resuelve en la base de datos. Si se hiciera sobre una List<Cita> ya cargada en memoria, se estaría descargando toda la tabla para filtrarla en C# — mucho más lento a medida que crece. Regla del proyecto: Where/OrderBy/Skip/Take siempre en el Repository sobre IQueryable (CLAUDE.md §4.9).

Las migraciones (Migrations/) son la otra mitad del ORM: generan el CREATE TABLE/ALTER TABLE automáticamente a partir de los cambios en Models/, con dotnet ef migrations add + dotnet ef database update.

El mismo ejemplo, sin ORM (SQL directo con ADO.NET)

Así se vería la misma consulta escrita a mano con NpgsqlCommand — tal como se hacía antes de los ORMs. Nadie en este proyecto escribe código así; es solo referencia.

using var connection = new NpgsqlConnection(connectionString);
await connection.OpenAsync();

var sql = @"
    SELECT c.""Id"", c.""FechaCita"", c.""Estado"",
           m.""Id"" AS mascota_id, m.""Nombre"" AS mascota_nombre,
           cl.""Nombre"" AS cliente_nombre, d.""Nombre"" AS doctor_nombre
    FROM ""Citas"" c
    LEFT JOIN ""Mascotas"" m ON m.""Id"" = c.""MascotaId""
    LEFT JOIN ""Clientes"" cl ON cl.""Id"" = m.""ClienteId""
    LEFT JOIN ""Usuarios"" d ON d.""Id"" = c.""DoctorId""
    WHERE (@doctorId IS NULL OR c.""DoctorId"" = @doctorId)
    ORDER BY c.""FechaCita"" DESC
    OFFSET @skip LIMIT @pageSize;
";

using var command = new NpgsqlCommand(sql, connection);
command.Parameters.AddWithValue("doctorId", doctorId.HasValue ? (object)doctorId.Value : DBNull.Value);
command.Parameters.AddWithValue("skip", (pageNumber - 1) * pageSize);

var citas = new List<Cita>();
using var reader = await command.ExecuteReaderAsync();
while (await reader.ReadAsync())
{
    // Hay que mapear cada columna a mano, campo por campo
    citas.Add(new Cita {
        Id = reader.GetInt32(reader.GetOrdinal("Id")),
        Estado = reader.IsDBNull(reader.GetOrdinal("Estado")) ? null : reader.GetString(reader.GetOrdinal("Estado")),
        Mascota = new Mascota { Nombre = reader.GetString(reader.GetOrdinal("mascota_nombre")) }
    });
}
// Y aparte, otra query completa solo para el COUNT(*) del total...
Sin ORM (ADO.NET)Con ORM (EF Core)
El SQLSe escribe a mano, como textoLo genera EF Core desde .Where(), .Include(), .OrderBy()
Mapeo fila → objetoManual, columna por columnaAutomático: devuelve List<Cita> con relaciones pobladas
Relaciones (JOIN)Hay que escribirlos y mapear cada tabla.Include().ThenInclude() — EF Core arma el JOIN solo
Cambiar Postgres ↔ MySQLRevisar sintaxis específica de cada motorAutomático según el proveedor configurado
Riesgo de SQL injectionAlto si se concatenan stringsBajo por diseño: LINQ siempre parametriza
Cantidad de códigoMucho código repetitivo por entidadUna línea de LINQ por consulta

El ORM no es "magia": automatiza exactamente ese trabajo (escribir el SQL, enviarlo, leer el resultado, mapearlo a objetos) para no repetirlo a mano en cada Repository.

Frontend: hook → servicio API → componente

Componente (JSX)  →  Hook (src/hooks/*.js)  →  src/services/api/index.js  →  client.js  →  (red)
  • El componente solo pinta UI y delega el fetch de datos a un hook.
  • El hook (ej. useGetCitas) maneja estado de carga/error y llama a una función de servicio (ej. getCitas()).
  • La función de servicio, en src/services/api/index.js, sabe el endpoint y los query params, pero delega el fetch real a request().
  • client.js es la única pieza que sabe de tokens, prefijos de ruta, manejo de 401 y parseo de la respuesta.

05Cómo arma la pantalla el frontend

Más allá de llamar a la API, cada pantalla se construye combinando varias fuentes separadas — nunca escritas "a mano" dentro del JSX.

Colores y estilos → variables CSS + módulos CSS

Todos los colores, sombras, radios y gradientes están centralizados como variables CSS en un único archivo:

vet-system-WEB/src/styles/variables.css 
:root {
  --button-blue: linear-gradient(135deg, #0284c7, #0369a1);
  --color-primary: rgb(23, 23, 255);
  --color-danger: #ea1f1f;
  --radius-md: 0.5rem;
  --shadow-md: 0 4px 6px -1px rgb(0 0 0 / 0.1), 0 2px 4px -2px rgb(0 0 0 / 0.1);
}

Ningún componente escribe un color literal en su JSX. Cada componente tiene su index.module.css que consume esas variables:

/* ejemplo de un .module.css cualquiera */
.button {
  background: var(--button-blue);
  border-radius: var(--radius-md);
  box-shadow: var(--shadow-md);
}
import styles from './index.module.css';
<button className={styles.button}>Guardar</button>
⚠ Regla dura del proyecto: "no se permite CSS inline ni hardcodeado en JSX". Un color nuevo primero se define en variables.css.

Textos → archivos de constantes

Ningún label, placeholder o mensaje se escribe como string literal en el JSX. Se centralizan en src/constants/:

vet-system-WEB/src/constants/TEXT.js 
export const TEXT_INVOICES_GESTION = {
  gestioPagos: "Gestion de pagos",
  paidtTotal: "Total pagado",
  refreshButton: "Refrescar",
  searchPlaceholder: "Buscar...",
};
import { TEXT_INVOICES_GESTION } from '../../constants/TEXT';
<h2>{TEXT_INVOICES_GESTION.gestioPagos}</h2>

Esto permite cambiar la redacción de toda la app desde un solo lugar, sin buscar el texto componente por componente.

Componentes → librería interna anteriority-ui primero

Antes de construir un botón, input o modal desde cero, la regla es revisar el catálogo de anteriority-ui — la librería de diseño interna con ~50 componentes listos. Ejemplos reales:

// vet-system-WEB/src/pages/DoctorSystem/CreateCustomerAndPets/CustomerAndPets.jsx
import { Input, ProfileAvatar } from 'anteriority-ui';

// vet-system-WEB/src/pages/AdminSystem/.../CurrencySelector.jsx
import { Loading, PlaceholderButton, Checks } from 'anteriority-ui';

Solo si la librería no tiene un equivalente, se cae al set local en src/components/screens/components/, siguiendo las mismas convenciones.

En resumen, una pantalla combina:

JSX del componente
 ├─ Texto      → import desde src/constants/TEXT.js (o constansts.js)
 ├─ Estilo     → import styles from './index.module.css' (usa var(--algo) de variables.css)
 ├─ Componente → import { Boton, Input, ... } from 'anteriority-ui' (o local si no existe)
 └─ Datos      → hook propio (src/hooks/*.js) que llama a src/services/api/index.js

Anatomía de un componente real: Filter

El panel de filtros reutilizable que aparece en varias pantallas de listados.

vet-system-WEB/src/components/screens/components/Filter/Index.jsx 
import React, { useState } from 'react';
import { Filter as FilterIcon, Trash2, Search } from 'lucide-react';
import DrawPanel from '../DrawPanel/index';
import Button from '../Button/index';
import styles from './Index.module.css';
import ModalTooltip from '../../../ModalTooltip/ModalTooltip';

const Filter = ({
    children, onClear, onApply,
    searchTerm = '', width = '350px', title = 'Filtros', activeFiltersCount = 0
}) => {
    const [isOpen, setIsOpen] = useState(false);

    const handleApply = () => {
        setIsOpen(false);
        if (onApply) onApply();
    };

    return (
        <div className={styles.filterWrapper}>
            <Button onClick={() => setIsOpen(true)} variant={Button.VARIANTS.PRIMARY}>
                <FilterIcon size={18} /> Filtrar
            </Button>
            {activeFiltersCount > 0 && (
                <span className={styles.filterBadge}>{activeFiltersCount}</span>
            )}
            <DrawPanel isOpen={isOpen} onClose={() => setIsOpen(false)} title={title} width={width}>
                <div className={styles.fields}>{children}</div>
                <Button onClick={handleApply}>Aplicar</Button>
            </DrawPanel>
        </div>
    );
};

export default Filter;

Importaciones

Un componente nunca trae su propia lógica o estilos sueltos: importa todo lo que necesita.

  • useState de 'react' → el hook para manejar estado local.
  • lucide-react → librería de íconos.
  • DrawPanel y Button → otros componentes locales del mismo catálogo — uno complejo se construye combinando otros más simples.
  • styles from './Index.module.css' → el CSS Module propio de este componente.
  • ModalTooltip → otro componente compartido, importado con ruta relativa.

Props — los "parámetros" del componente

Filter recibe un único objeto, desestructurado en la firma. Son las props: valores que quien lo usa le pasa desde afuera.

<Filter title="Filtrar facturas" activeFiltersCount={2} onApply={handleApplyFilters}>
  <input ... />
</Filter>
  • title, width, activeFiltersCount tienen valores por defecto: si no se pasan, el componente usa esos.
  • onApply y onClear son callbacks: el padre decide qué pasa; el hijo solo ejecuta la función en el momento correcto.
  • children es una prop especial: todo lo que va entre las etiquetas de apertura y cierre — así Filter envuelve cualquier formulario sin conocer sus campos.

useState — estado local

const [isOpen, setIsOpen] = useState(false);

Crea una variable isOpen y una función setIsOpen para cambiarla. Cada setIsOpen(true) hace que React vuelva a renderizar con el nuevo valor — así se abre o cierra el panel sin tocar el DOM a mano. Es estado local: vive solo en este componente.

useEffect — código que reacciona a cambios

No está en Filter, pero sí en otros componentes del proyecto, ej. CountdownBar:

// vet-system-WEB/src/components/screens/components/CountdownBar/utils.js
useEffect(() => {
  if (!active) {
    setState({ progress: 100, remainingSeconds: durationRef.current / 1000 });
    return;
  }
  const timer = setInterval(() => { /* recalcula progreso cada 50ms */ }, 50);
  return () => clearInterval(timer); // limpieza al desmontar o cambiar "active"
}, [active]); // ← dependencias: solo re-corre si "active" cambió

Un array vacío [] significa "correr solo una vez, al montar" — el patrón típico para un fetch inicial, como en useGetCitas: useEffect(() => { if (autoFetch) fetchCitas(); }, [fetchCitas, autoFetch]).

Constantes dentro del componente

Valores derivados calculados en cada render, por ejemplo en CurrencySelector.jsx:

const isGlobalLoading = currencyLoading || bcvLoading;
const currencies = [
  { code: 'USD', icon: DollarSign, label: getText('moneySettings.dollar') },
  { code: 'VES', icon: Wallet, label: getText('moneySettings.bolivares') }
];

No se centralizan en constants/ porque dependen de datos en tiempo de ejecución — lo que sí va ahí son los textos fijos.

Render (el return)

Es la única parte que describe qué se ve: JSX que combina props, estado y componentes importados. No contiene lógica compleja — regla de "separar lógica de presentación".

06Otros flujos importantes

🧾Facturación: una cita completada genera una consulta médica, que descuenta stock de productos usados y calcula el total (con conversión Bolívares/Dólares vía la tasa BCV que un Worker actualiza a diario). La factura se genera como PDF con QuestPDF y se guarda en wwwroot/.
💬Mensajería y notificaciones: en tiempo real vía SignalR (MessageHub, NotificactionsPush), agrupando conexiones por userId y rol.
🛟Tolerancia a fallos: el frontend chequea la salud de la API cada 10s (useHealthCheck) y redirige a /espera si detecta que el backend o internet están caídos, restaurando la vista anterior al reconectar.
⏱️Workers en segundo plano: tareas programadas del backend (actualizar tasa BCV, limpiar PDFs/reportes viejos, generar reportes automáticos) corren independientes de cualquier request HTTP.
